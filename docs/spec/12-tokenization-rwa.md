# 12. Токенизация недвижимости GROUNDZ — модель RWA + RFQ

> Адаптация гайда «SAI Wallet — минимальная модель интеграции RWA и RFQ» (SAI Labs, июль 2026)
> под инвестиционную платформу GROUNDZ ESTATE. Статус: DRAFT, июль 2026.
> Источник: `SAI_Wallet_RWA_RFQ_Minimal_Guide_RU.pdf` (корень репозитория-родителя).

## 0. Три типа токенов Groundz

| Токен | Стандарт | Что даёт | Чем НЕ является |
|---|---|---|---|
| **RWA-токен пула** (`Pool.tokenSymbol`) | ERC-3643 (permissioned) | Долю в экономике конкретного пула недвижимости: арендный доход + доход от выхода (продажа/рефинанс) по заранее зафиксированной формуле | Не «токен компании»: каждый пул — отдельный выпуск со своей экономикой |
| **Utility-токен сервиса** | ERC-20 (обычный) | Сервисные привилегии: уровни членства (`MembershipTier`), скидки на комиссии платформы, ранний доступ к пресейлам пулов, голосования, партнёрские офферы | Не даёт долю в доходе — не security. Никаких обещаний доходности |
| **NFT-сертификат** (опционально, фаза 2) | ERC-721 (рекоменд. soulbound) | Ончейн-подтверждение: участия в конкретном пуле, статуса инвестора (tier), завершённого цикла «вложил → получил выплаты → вышел» | Не передаёт права на доход (право — у RWA-токена); это верифицируемый бейдж/сертификат |

Принцип из гайда, который сохраняем дословно: **один пул = один отдельный RWA-выпуск**
со своей экономикой, бюджетом и правилами распределения (в гайде это «сезон клуба»).
После завершения пула токены гасятся/сжигаются, а подтверждением участия остаётся
NFT-сертификат.

## 1. Границы ответственности

| GROUNDZ (платформа) | Third-party провайдеры | Застройщик / SPV пула |
|---|---|---|
| Витрина пулов: карточка объекта, параметры выпуска, документы data-room, статусы строительства | Разворачивают ERC-3643 контракт, выпускают supply, управляют ролями токена | Передаёт данные объекта: смета, сроки, формула дохода, график выплат |
| KYC/AML onboarding, sanctions/PEP screening, KYT — через интегрированных провайдеров | Возвращают eligibility status для конкретной операции | Обновляет отчётность по стройке (`ConstructionReport`) и события, влияющие на выплаты |
| Передаёт RFQ-запрос инвестора, показывает котировку | Формируют firm quote, исполняют покупку/продажу | Получает средства первичного размещения через внешний settlement-контур |
| Показывает статус сделки, токена и выплат по webhooks/API | Принимают, хранят и распределяют fiat/crypto; settlement, redemption, выплаты дохода | Финансирует выплаты держателям через issuer / paying agent |

**Ключевое: Groundz не принимает и не распределяет клиентские fiat/crypto.**
Средства идут напрямую: инвестор → SPV пула (первичка), покупатель → продавец
(вторичка через OTC), issuer/paying agent → держатель (доход). Это снимает с
платформы лицензионную нагрузку кастодиана/платёжного института.

## 2. Поток покупки доли пула

| Шаг | Этап | Что происходит |
|---|---|---|
| 1 | Витрина | Groundz отдаёт список пулов и параметры выпуска (Pool Catalog = наш `/pools` + API) |
| 2 | Проверка | Инвестор проходит KYC/AML в Groundz (раздел `/admin/kyc` уже есть); провайдер возвращает eligibility для выбранного пула |
| 3 | RFQ | Инвестор задаёт side и amount; Groundz отправляет запрос во внешний RFQ API |
| 4 | Котировка | RFQ-провайдер возвращает цену, комиссии, TTL и settlement instructions |
| 5 | Подтверждение | Инвестор подтверждает quote, подписывает сообщение/транзакцию кошельком |
| 6 | Исполнение | Third party исполняет trade и settlement вне Groundz |
| 7 | Доставка | RWA-токены пула поступают в кошелёк инвестора; средства — в SPV пула |
| 8 | Статус | Webhooks обновляют сделку: completed / failed / expired / refunded → пишем в `Transaction` |

Вторичный рынок: существующий OTC-модуль (`/otc`) становится интерфейсом RFQ
для перепродажи RWA-токенов между проверенными инвесторами — листинг, оффер,
accept уже смоделированы; исполнение уходит внешнему провайдеру.

## 3. Движение средств

| Сценарий | Получатель средств | Роль Groundz |
|---|---|---|
| Первичная покупка доли пула | SPV пула / назначенный settlement account | Показывает quote и статус; не принимает средства |
| Вторичная продажа (OTC) | Продавец, через внешний settlement-контур | Передаёт RFQ и отображает результат |
| Арендный доход / доход от выхода | Держатель RWA напрямую от issuer / paying agent | Показывает начисление, выплату и историю (`Transaction` feed в кабинете) |
| Покупка utility-токена | Платформа (это наш собственный продукт) | Единственный сценарий, где Groundz — получатель |

## 4. Минимальные API-контракты

Как в гайде, с маппингом на платформу:

| API | Операции | Маппинг Groundz |
|---|---|---|
| Pool Catalog | `GET /assets`, `GET /assets/{id}` | наши `Pool` + chain, contract, price source, доступность |
| Eligibility | `POST /eligibility/check` → allowed / review / denied + expiry | вход: `user_id`, wallet, `pool_id`; KYC-статус уже в модели пользователя |
| RFQ | `POST /quotes`, `POST /quotes/{id}/accept` | side, amount, валюта, fees, TTL |
| Trade / Settlement | `GET /trades/{id}`, `GET /settlements/{id}` | state, tx hash / payment reference → `Transaction` |
| Payouts | `GET /payouts` + webhook | record date, amount, currency, status → `Transaction` (type: distribution) |
| Webhooks | `quote.expired`, `trade.updated`, `settlement.updated`, `payout.updated` | подписанные и идемпотентные |

## 5. Минимальная конфигурация MVP

- Один пул, одна EVM-сеть, один внешний RFQ-провайдер.
- **RWA: ERC-3643** — нужны allowlist, transfer restrictions, pause/freeze, recovery.
  Роли контракта (`tokenAgent`, `complianceAgent`, `treasury`, `payoutSigner`) — у
  issuer/operator, разделены, под multisig.
- **Utility: обычный ERC-20** без ограничений трансфера (сервисный, не security).
- **NFT-сертификаты — не в MVP.** Добавляются фазой 2, когда закрыт end-to-end цикл RWA.
- Один settlement rail (fiat или stablecoin), только firm quotes — без своего
  order book и market making.
- State machine сделки: `created → quoted → accepted → settling → completed / failed / expired / refunded`;
  idempotency key, подписанные webhooks, audit log (наш непробиваемый audit — Hard rule #2).
- **Fail closed:** при недоступности eligibility/RFQ API, истёкшем KYC или неизвестном
  статусе операция не продолжается.

## 6. Whitelist и выпуск токенов (порядок эмитента)

1. Получить от Groundz результат KYC/AML и eligibility.
2. Подтвердить владение кошельком подписью одноразового сообщения.
3. Создать/связать кошелёк с ONCHAINID.
4. Добавить identity claims.
5. Зарегистрировать адрес в Identity Registry.
6. Проверить `isVerified(wallet)`.
7. Только после этого — `mint(wallet, amount)`.

Статусы адреса: `pending → verified → active → expired / revoked`.
Токены выпускаются **только после** фактического поступления средств, нужного числа
confirmations и KYT-проверки. Недоплата, переплата, просрочка, возврат — отдельные
статусы PaymentIntent.

## 7. Распределение дохода пула

Для каждого периода (квартальная аренда; финальный exit) issuer определяет:
`distribution_id`, дату и `snapshot_block`, формулу, валюту, общую сумму, окно выплат.

```
выплата = распределяемая сумма × баланс на snapshot / общий eligible supply
```

- Баланс фиксируется на `snapshot_block` через indexer/archive node — **не** текущий `balanceOf`.
- Crypto: claim-based модель (payout manifest → Merkle root → контракт с USDC/USDT → держатель вызывает `claim`); при малом числе держателей — batch transfer.
- Fiat: payout-провайдер на подтверждённые реквизиты.
- **Без rebase**: supply RWA неизменен, доход выплачивается отдельным активом.
- Каждая выплата: `distribution_id, wallet, snapshot_balance, gross_amount, net_amount, currency, tx_hash/payment_reference, status` → синк в `Transaction`.

В распределяемый пул входит только заранее зафиксированная доля и методика расчёта
(процент от аренды, доля от суммы продажи) — не вся выручка проекта. Это прямой
аналог правила «доля доходов сезона» из кейса гайда.

> Дисклеймер (обязателен на каждой карточке пула — см. AEO-правила SEO-модуля):
> расчёт является прогнозным и не гарантирует получение дохода. Если предусмотренный
> правилами пул распределения не сформирован, выплата может быть нулевой.

## 8. NFT-сертификаты (фаза 2)

- **Сертификат участия в пуле**: минтится при первой покупке RWA-токенов пула; после
  redemption пула остаётся ончейн-подтверждением завершённого цикла (в гайде — «токены
  сожжены либо остаются как цифровое подтверждение участия»; мы делаем это отдельным
  ERC-721, чтобы RWA можно было чисто гасить).
- **Сертификат статуса**: привязан к `MembershipTier` (bronze/silver/gold…); обновляется
  при смене уровня. Рекомендуется soulbound (non-transferable), иначе статус можно продать.
- Проверка привилегий: платформа подтверждает владение нужным количеством
  utility-токенов / наличием NFT **без передачи контроля над кошельком** (подпись
  сообщения, как в кейсе клубных привилегий).

## 9. Инструкция запуска (адаптированная)

1. **Зафиксировать экономику пула**: объект, объём выпуска, цена токена, срок,
   формула дохода (аренда + exit), график выплат, погашение.
2. **Выбрать внешних исполнителей**: issuance/tokenization, RFQ/trading,
   settlement/payout. Для MVP один провайдер может закрывать несколько функций.
3. **Подготовить выпуск**: карточка пула в Groundz; third party разворачивает
   ERC-3643, выпускает supply, передаёт contract metadata (`Pool.tokenSymbol`,
   `totalTokens`, `pricePerToken` уже в схеме).
4. **Подключить AML/KYC**: Groundz собирает данные и screening; провайдер возвращает
   eligibility.
5. **Интегрировать RFQ и settlement**: quote, accept, trade status, settlement status,
   подписанные webhooks.
6. **Протестировать полный цикл**: покупка, продажа, expired quote, denied eligibility,
   failed settlement, refund, payout, повтор webhook.
7. **Пилот**: один пул, малая группа инвесторов; сети/валюты/провайдеры — после
   стабильного end-to-end. Utility-токен и NFT — после пилота RWA.

## 10. Критерии готовности к запуску

- Eligibility проверяется перед каждым quote и повторно перед исполнением.
- Groundz не контролирует адреса/счета, через которые проходят клиентские средства.
- Каждый trade и payout имеет внешний reference и восстанавливается после повторного webhook.
- В интерфейсе пула явно указаны поставщики выпуска, RFQ, settlement и payout.
- Команда прошла end-to-end тесты и обрабатывает failed / expired / refunded.

## 11. Что уже есть в платформе / чего не хватает

| Реализовано (миграция `add_tokenization_models`, 2026-07-31) | Осталось (бэклог) |
|---|---|
| `WalletAddress` со статусной моделью pending/verified/active/expired/revoked; добавление в `/investor/wallet`, верификация командой в админке | Подтверждение владения кошельком подписью сообщения (сейчас — ручная верификация) |
| `PaymentIntent` (payment_reference, TTL 72ч, статусы недоплаты/возврата); state-machine запрещает mint до confirmed | Реальные реквизиты/deposit address от settlement-провайдера в `transferDetails` |
| `Distribution` + `DistributionPayout`: snapshot держателей, формула total × balance / eligible supply (floor до цента), выплаты → `Transaction` | On-chain snapshot по блоку (сейчас — DB-балансы `Holding`), Merkle-claim контракт |
| Fail-closed eligibility: роль + approved KYC-документ + верифицированный кошелёк | Интеграции: Asset Catalog / RFQ / Settlement / Payout API внешних провайдеров + подписанные webhooks |
| Админ-операции: `/admin/investment-pools/[id]/tokenization`; mint ведёт платформенный леджер (tokensSold, Holding, Transaction) | Utility-токен и NFT-сертификаты (фаза 2), ERC-3643 деплой у issuer |

Серверный модуль: `src/lib/server/tokenization/` (status.ts — state-machines,
payouts.ts — чистая математика выплат, service.ts — DB-флоу). Тесты: `npm run test:tokenization`.
